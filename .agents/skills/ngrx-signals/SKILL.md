# NgRx Signals

Every mutable value has one **owner**: the store or feature responsible for its transitions. Public methods, reducers, and success reconciliation may implement several transitions within that owner. Derived values read their sources instead of keeping synchronized copies. This is an architectural convention, not an NgRx restriction on how many methods may call `patchState`.

## Workflow

1. Read the target application's dependency declarations and lockfile, including its owning workspace package in a monorepo, not the skill directory's dependencies. Establish versions and API owners using [version gates](references/testing-and-version-gates.md). Read installed declarations when docs disagree. With no project, state the reference baseline as an assumption. Finish with every proposed import assigned to a supported package and version.
2. For new store reads/writes with Toolkit installed, or any Toolkit adoption, migration, or API task, read the sibling [ngrx-toolkit skill](../ngrx-toolkit/SKILL.md) and apply its selection policy before choosing adapters. Then assign each changed value an owner and each asynchronous operation a concurrency and error policy using the table below.
3. Read the matching references below. Use the combined recipe only for a task combining its flows. Read version-specific docs through Context7, then primary guides or tagged source for gaps; a stale index is not evidence that an API is absent.
4. Implement the smallest change. Feature order follows actual dependencies. Toolkit is optional, including on NgRx v22.
5. Test each changed transition, including failure and cancellation where relevant. For advice or review without executable code, identify the required tests and label checks not run.

## Owner table

| Value role                              | Owner                                                                                                                                                                                                         | Written by                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Request input — query, id, filter, page | `withState` slice                                                                                                                                                                                             | store method, reactive `signalMethod`, or event reducer              |
| Server data                             | Angular resource held in `withProps`, Toolkit `withResource`, a [route `resources` entry](references/testing-and-version-gates.md#upgrade-to-v22) keyed only on the URL, or an existing store-owned load flow | request dependencies or explicit load/reconciliation commands        |
| Derived presentation value              | `withComputed`                                                                                                                                                                                                | nothing — it recomputes                                              |
| Derived value that must stay writable   | `withLinkedState`                                                                                                                                                                                             | `patchState`, and its source recomputing                             |
| Editable draft                          | `withState` or `withLinkedState`                                                                                                                                                                              | a store method, fed from a live form by `linkedSignal({ set })`      |
| Backend write and its status            | Toolkit `withMutations` or the existing command flow                                                                                                                                                          | the command that calls it                                            |
| Collection needing lookups by id        | Toolkit `withEntityResources` for resource-backed arrays, or native `withEntities` for store-owned collections                                                                                                | resource projections or entity updaters with an explicit load policy |

Use a plain method for an imperative transition, `signalMethod` for reactive signal inputs, and `rxMethod` for stream semantics. Prefer the store's existing transition style. Resources model reads; commands model writes. HTTP verbs alone do not decide whether an operation is a read, such as a POST-based search.

## Completion criteria

Finish when every changed mutable value has an owner, every changed dependency or transition has a focused check, and imports match the target versions. For resource/mutation flows, verify visible error handling and reconciliation. For Toolkit mutations, cover every awaited result branch: `success`, `error`, and `aborted`. Only confirmed success advances the UI; cancellation does not prove a server write was rolled back.
