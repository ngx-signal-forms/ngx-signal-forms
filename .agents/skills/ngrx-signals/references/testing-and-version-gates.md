# Version gates and testing

## Baseline

Checked 2026-09-29. Examples target **Angular 22.1+**, with 22.2 features gated below, **`@ngrx/signals` 22.0.1+**, and, where needed, **`@ngrx-toolkit/core` 22.0.1**. These are documentation targets, not dependencies installed in this skill workspace. Read the application's lockfile and installed declarations first.

### Upgrade to v22

The [NgRx migration guide](https://ngrx.io/guide/migration/v22) requires Angular/CLI 22, TypeScript 6.0, and RxJS `^6.5.x || ^7.5.0`. Toolkit's v22 tagged manifest requires Angular core/common and NgRx Signals `^22.0.0`, and RxJS `^7.0.0`. With both libraries, choose compatible RxJS 7.5+ within major 7.

1. Align Angular and NgRx majors. Run the applicable NgRx migration, `ng update @ngrx/signals@22`, or `ng update @ngrx/store@22` for Store-based projects, using the project's tooling.
2. For Toolkit v22, replace the old dependency and imports with `@ngrx-toolkit/core`, including secondary entry points. For v21 and earlier, retain `@angular-architects/ngrx-toolkit`. The reviewed release does not establish an automatic package-rename migration.
3. Remove only peer overrides introduced for the temporary Angular 22/NgRx 21 combination. Reinstall with normal peer validation; retain unrelated overrides.
4. Review dynamic union types and generic features, replace callback-style `tapResponse` with `{ next, error, complete? }`, and use ESLint flat config. NgRx v22 drops ESLint 8 and supports 9/10.
5. Type-check and run the affected tests. A major number or successful install does not establish compatibility for every experimental API.

The `ng update` schematics fix only some breaking changes. Review union-typed slices and generic feature annotations by hand. NgRx 22.0.0 shipped on 2026-08-24 and 22.0.1 on 2026-09-10. Base API decisions on the installed version's declarations, not on changelog headings.

## Focused reactive tests

Test the edges of the graph, not the shape of the store:

1. **Request input → resource**: change a store input through its public boundary; assert the resource issues the new request and its value or status follows.
2. **Form → draft**: set a Signal Form field; assert the model signal and the store draft both update immediately.
3. **Draft → form**: write the draft through its store boundary; assert the form model reacts.
4. **Mutation success → read model**: resolve a mutation; assert the response patches the resource-backed state or the reload runs.
5. **Mutation failure → surface**: reject a mutation; assert the error reaches its destination — a `submit()` form error, an error signal read by the template — and that good data is unchanged.
6. **Mutation abort → not saved**: fire the duplicate call the chosen operator drops; assert the aborted result never takes a success path — no navigation, no closed dialog, no cleared form.
7. **Resource failure**: test first-load and later errors; assert the UI takes its error branch and guards potentially throwing value reads. Toolkit's `"previous value"` policy caches each successful observed read, including `undefined`; it may throw if the first read occurs in error. Do not assume it retains the last defined value.
8. **Concurrency**: fire the duplicate-command scenario the chosen operator is meant to handle, and assert the resulting call count.
9. **Derivation**: change one source of a combined view model; assert the computed follows and reports absence while a required source is missing. Missing optional enrichment uses its declared fallback without hiding the required data.
10. **Contract**: feed an invalid response and assert the resource or mutation enters its error path; feed an invalid form value and assert field errors appear.
11. **Event → consumer**: dispatch the event and assert each consuming store reacted — the reducer changed its request state, and the resource that reads that state issued a new request. Assert both consumers, since the point of the event is that neither knows about the other.
12. **Native extension scope**: assert parent/child/local precedence, loading and error fallbacks, and that a bare resource is unaffected by provider defaults.
13. **Union types**: type-check object/null and object/object slices plus a generic feature consumer. Assert the derived view follows transitions in both directions.
14. **Toolkit generated members**: compile snapshot and named/unnamed resource guards. Use only pending/status/error aliases on `withMutations` methods. In 22.0.1, named mutation error aliases are declared `Error | undefined` despite runtime errors being unknown; narrow defensively rather than assuming normalization.
15. **Save races**: switch selection and edit again while a save is pending. For the current session, a successful save of S1 advances the stable baseline to S1 while preserving a newer draft S2. Assert dirty state compares S2 with S1 even through refetch or transient missing data. An old-session response must not change the current baseline or draft. Cancellation tests must not infer server rollback.

### The harness

`TestBed.tick()` synchronizes Angular work, including effects; it does not advance elapsed time or satisfy a 250 ms debounce. Use it for reactive `signalMethod` inputs before asserting their effects. Static inputs apply synchronously.

This boundary-only fixture tests paging reset without resources, HTTP, or timers:

```ts
import { TestBed } from '@angular/core/testing';
import {
  patchState,
  signalMethod,
  signalStore,
  withMethods,
  withState,
} from '@ngrx/signals';

const SearchBoundaryStore = signalStore(
  withState({ query: '', page: 1 }),
  withMethods((store) => ({
    setPage: signalMethod<number>((page) => patchState(store, { page })),
    setQuery: signalMethod<string>((query) =>
      patchState(store, { query, page: 1 }),
    ),
  })),
);

describe('SearchBoundaryStore', () => {
  let store: InstanceType<typeof SearchBoundaryStore>;

  beforeEach(() => {
    TestBed.configureTestingModule({
      providers: [SearchBoundaryStore],
    });
    store = TestBed.inject(SearchBoundaryStore);
  });

  it('resets page 3 to page 1 synchronously when the query changes', () => {
    store.setPage(3);
    expect(store.page()).toBe(3);

    store.setQuery('angular');

    expect(store.query()).toBe('angular');
    expect(store.page()).toBe(1);
  });
});
```

Test the real store's request flow separately. Provide the HTTP test backend and handle any initial request before changing inputs, or explicitly account for its cancellation. For a 250 ms debounce, advance the configured runner's timers by that interval or wait for it using the supported async setup, then settle Angular effects and resource work before expecting the new request. Flush the response, settle again, and assert the value and status. Verify outstanding HTTP requests at teardown. `TestBed.tick()` alone is not a timer advance.

For an editor store configured with `exhaustOp`, start one save with a valid fixture, call it again before flushing HTTP, and assert the second result is `aborted`. Then flush the first request and assert its result is `success`. Keep this in the editor's suite rather than adding save methods to the search-store fixture above.

Two rules the rest of the list depends on:

- **Call a reactive `signalMethod` inside an injection context**, and `TestBed.tick()` before asserting. A `signalMethod` called with a static value applies synchronously and needs no flush.
- **A mapping function extracted from a computed is tested directly** — no `TestBed`, no injector, no signals. Prefer that wherever the logic allows it.

## Completion criteria

Run the focused test target after implementing. Every read, write, and synchronisation edge that changed must be covered by a new test or an existing equivalent.
