# Migration to v1.0.0-rc.12

## Upgrade from v1.0.0-rc.11

This release removes two single-adapter helpers (`toHintDescriptors`,
`createErrorRendererInputs`) from the public `/headless` surface, moves the
internal `resolveUnionInput` out of `/core` (never a published entry point),
and folds `NgxFormFieldNotification` into `NgxFormFieldError`.

### Required changes

- **`toHintDescriptors` and `createErrorRendererInputs` are removed** from
  `@ngx-signal-forms/toolkit/headless` (and their option/return types
  `CreateErrorRendererInputsOptions`, `HintLike`,
  `NgxFormFieldErrorRendererInputs`). Both had exactly one first-party
  adapter (the form-field wrapper) plus the reference custom wrappers in the
  demo apps, and each is a single `computed()` — inline it directly instead
  of importing a shared helper:

  ```ts
  // Hint descriptors for NGX_SIGNAL_FORM_HINT_REGISTRY
  readonly hintDescriptors = computed(() =>
    this.hintChildren().map((hint) => ({
      id: hint.resolvedId(),
      fieldName: hint.resolvedFieldName(),
    })),
  );

  // *ngComponentOutlet inputs for a custom error renderer
  readonly errorRendererInputs = computed<Record<string, unknown>>(() => ({
    formField: this.formField(),
    strategy: this.effectiveStrategy(),
    submittedStatus: this.submittedStatus(),
  }));
  ```

- **`resolveUnionInput` is removed** from `@ngx-signal-forms/toolkit/core`
  (and `ResolveUnionInputOptions`). It was never part of a published entry
  point (`/core` is stripped from the published `exports` map) and had only
  two adapters, both inside `@ngx-signal-forms/toolkit/form-field`. If you
  copied its "membership test → one-shot dev warning → fallback" shape for
  your own string-union inputs, keep your own copy — there is no
  replacement export.

- **`NgxFormFieldNotification` (`<ngx-form-field-notification>`) is
  removed** from `@ngx-signal-forms/toolkit/assistive`, along with
  `NgxFormFieldNotificationListStyle`. Use `NgxFormFieldError` with the new
  `presentation="panel"` input instead — it accepts the same `errors`,
  `fieldName`, `title`, and `listStyle` inputs the notification component
  did:

  ```html
  <!-- Before -->
  <ngx-form-field-notification
    [errors]="groupedErrors"
    fieldName="address"
    title="Please review the following"
    listStyle="bullets"
  />

  <!-- After -->
  <ngx-form-field-error
    [errors]="groupedErrors"
    fieldName="address"
    title="Please review the following"
    listStyle="bullets"
    presentation="panel"
  />
  ```

  `presentation` defaults to `'inline'` (the shape `NgxFormFieldError`
  always rendered) — existing per-field usage needs no change.
  `NgxFormFieldset`'s own `feedbackAppearance`/`notificationTitle` inputs
  are unaffected; the fieldset now renders `ngx-form-field-error
presentation="panel"` internally instead of the deleted component.

- **CSS selectors and custom properties**: the `.ngx-form-field-notification*`
  classes are gone. `presentation="panel"` renders the same BEM classes as
  `presentation="inline"` (`.ngx-form-field-error`, `.ngx-form-field-error--error`,
  `.ngx-form-field-error__list`, `.ngx-form-field-error__message`, plus the
  new `.ngx-form-field-error__title`), gated by a `[data-presentation="panel"]`
  host attribute. The public custom properties are renamed to match:

  | Before                                                | After                                                                      |
  | ----------------------------------------------------- | -------------------------------------------------------------------------- |
  | `--ngx-signal-form-notification-padding`              | `--ngx-signal-form-error-panel-padding`                                    |
  | `--ngx-signal-form-notification-message-spacing`      | `--ngx-signal-form-error-panel-message-spacing`                            |
  | `--ngx-signal-form-notification-border-width`         | `--ngx-signal-form-error-panel-border-width`                               |
  | `--ngx-signal-form-notification-border-radius`        | `--ngx-signal-form-error-panel-border-radius`                              |
  | `--ngx-signal-form-notification-error-bg`             | `--ngx-signal-form-error-panel-bg`                                         |
  | `--ngx-signal-form-notification-error-color`          | `--ngx-signal-form-error-panel-color`                                      |
  | `--ngx-signal-form-notification-error-border-color`   | `--ngx-signal-form-error-panel-border-color`                               |
  | `--ngx-signal-form-notification-warning-bg`           | `--ngx-signal-form-warning-panel-bg`                                       |
  | `--ngx-signal-form-notification-warning-color`        | `--ngx-signal-form-warning-panel-color`                                    |
  | `--ngx-signal-form-notification-warning-border-color` | `--ngx-signal-form-warning-panel-border-color`                             |
  | `--ngx-signal-form-notification-title-color`          | `--ngx-signal-form-error-title-color` _(shared across both presentations)_ |
  | `--ngx-signal-form-notification-font-size`            | `--ngx-signal-form-error-panel-font-size`                                  |
  | `--ngx-signal-form-notification-line-height`          | `--ngx-signal-form-error-panel-line-height`                                |

`NgxHeadlessNotification` (`@ngx-signal-forms/toolkit/headless`) is
**unaffected** — it remains available for custom grouped-notification UIs
built from scratch. `NgxFormFieldError`'s `presentation="panel"` mode does
not use it; it composes `NgxHeadlessErrorState`'s existing errors-override
mode instead (see the class doc comment on `NgxFormFieldError` for why).
