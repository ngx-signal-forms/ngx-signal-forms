# Migration to v1.0.0-rc.16

## Upgrade from v1.0.0-rc.15

Scope: the RC.15-to-RC.16 upgrade. Two defaults changed in the form field
wrapper's CSS, and every toolkit component now picks light or dark colors
from `color-scheme`. No TypeScript API changed.

### Upgrade checklist and compatibility

- [ ] Confirm the installed toolkit version is RC.15. For earlier versions,
      first follow the [migration index](./README.md).
- [ ] Select `1.0.0-rc.16` in your package manager. Update the dependency and
      lockfile together.
- [ ] Keep compatible peers. Angular common/core/forms remain
      `>=22.0.0 <23.0.0`; optional Vest remains `>=6.0.0 <7.0.0`, and optional
      axe-core remains `>=4.5.0`. See [compatibility](../../COMPATIBILITY.md)
      and the [package manifest](../../packages/toolkit/package.json).
- [ ] Build and run your existing type-check and tests.

### Required changes

<!-- Add one subsection per breaking change. State the before and after. -->

#### 1. `--ngx-form-field-border-color` now defaults to a darker, WCAG-compliant color

`--ngx-form-field-border-color` (which cascades from
`--ngx-form-field-color-border`) defaulted to `rgba(50, 65, 85, 0.25)` — a
border that met only 1.55:1 contrast against the field's white background
(2.21:1 in dark mode), below the WCAG 2.2 SC 1.4.11 (Non-text contrast) 3:1
floor. It is the only visible edge of a text input, so a low-vision user
could not always tell where a field ended.

It now defaults to `rgba(50, 65, 85, 0.7)` in light mode and
`rgba(249, 250, 251, 0.4)` in dark mode. WCAG 2.2 SC 1.4.11 exempts
disabled controls, so the 3:1 floor only applies to an enabled field. The
light-mode value clears 3:1 against every background an enabled field's
border was measured against: white (~4.35:1), `#f9fafb` (~4.17:1),
`#f3f4f6` (~3.96:1), and `#e5e7eb` (~3.52:1, a common page/card
background). `#f3f4f6` also happens to be `--ngx-form-field-color-disabled`
— the border clears 3:1 against it too, but that is incidental, not an
SC 1.4.11 requirement, since a disabled field is exempt. The dark-mode
value clears ~3.51:1 against the dark surface color (`#1f2937`). The
border reads darker (light mode) or lighter (dark mode) than before. If
your theme depends on the previous, lighter value, restore it explicitly:

```css
ngx-form-field-wrapper {
  --ngx-form-field-color-border: light-dark(
    rgba(50, 65, 85, 0.25),
    rgba(249, 250, 251, 0.25)
  );
}
```

A restored value below 3:1 re-introduces the original contrast failure —
prefer keeping the new default, or picking your own color at 3:1 or more,
over reverting.

#### 2. `--ngx-form-field-warning-box-shadow` now defaults to `none`

Before (the effective default — `--ngx-form-field-warning-color` has no
default of its own, so it needs the same fallback here that the wrapper
gives it internally):

```css
--ngx-form-field-warning-box-shadow: 0 0 0 4px
  color-mix(
    in srgb,
    var(--ngx-form-field-warning-color, #a16207) 25%,
    transparent
  );
```

After:

```css
--ngx-form-field-warning-box-shadow: none;
```

The 25%-opacity ring only reached 1.40:1 contrast on white — below the 3:1
floor — and a focused warning field now also draws a solid, higher-contrast
outline (see the addition below). Left at its old default, the ring would
sit in the same visual band as the new outline and double up. If you rely
on the ring, restore it:

```css
ngx-form-field-wrapper {
  --ngx-form-field-warning-box-shadow: 0 0 0 4px
    color-mix(
      in srgb,
      var(
          --ngx-form-field-warning-color,
          var(--ngx-form-field-color-warning, light-dark(#a16207, #fcd34d))
        )
        25%,
      transparent
    );
}
```

The `light-dark()` fallback matches the wrapper's own warning color in both
schemes, so the ring follows your app's `color-scheme` (see
[section 3](#3-dark-mode-follows-color-scheme-not-dark-or-the-os-query)).

The same change applies to the invalid state through the new
`--ngx-form-field-invalid-box-shadow` token — see the addition below; there
is no "before" value to restore since that token did not exist before this
release.

#### 3. Dark mode follows `color-scheme`, not `.dark` or the OS query

Before, the components used different dark-mode triggers:

- The wrapper switched on a `.dark` class through `:host-context()`. When
  the OS preferred dark and `.dark` was absent, it forced light colors.
- The error component switched on `prefers-color-scheme` only. In a light
  app on a dark OS, error text was `#fca5a5` on white (1.90:1) and warning
  text was `#fcd34d` on white (1.44:1).
- The hint, character count, marking legend, fieldset and error summary had
  no dark colors. In a `.dark` app, hint and count text was 1.29:1.

Now every color default is a `light-dark(<light>, <dark>)` pair. The
browser picks the side from the element's used `color-scheme`. The toolkit
has no `prefers-color-scheme` or `:host-context(.dark)` color rules left.
Public token names do not change, and a value you set on a public token
still wins.

An app that declares no `color-scheme` gets light colors, also on a dark
OS. If your app relied on the OS query or on a `.dark` class, declare the
scheme:

```css
/* Follow the OS (replaces the old prefers-color-scheme behavior) */
:root {
  color-scheme: light dark;
}

/* Or: class toggle (replaces the old .dark detection) */
:root {
  color-scheme: light;
}

:root.dark {
  color-scheme: dark;
}
```

If you set `--ngx-signal-form-error-color`, `--ngx-signal-form-warning-color`
or other color tokens per theme only to work around the old triggers, remove
those overrides. A single value on a token applies in both schemes; use
`light-dark()` in your own value to keep separate light and dark colors.

Other consumer-visible changes that ship with this release, none of them
requiring an action unless you built on the removed internals:

- A focused standard or outline-appearance textual field now draws a solid,
  2px outline (see the addition below) in addition to its existing
  border-color and box-shadow changes. If you already override
  `--ngx-form-field-focus-color`, the outline picks it up automatically.
- The invalid state's box-shadow ring is no longer built from an inlined,
  non-overridable `color-mix()` expression. It is now driven by the new
  `--ngx-form-field-invalid-box-shadow` token (default `none`).
- `--ngx-form-field-state-ring-opacity` no longer affects the invalid or
  warning rings, since both default to `none`. It still controls the
  focus-color ring on a valid field (`--ngx-form-field-focus-box-shadow`),
  which is unchanged.

### Additions and compatibility

<!-- Add one bullet per additive change. -->

- A focused textual field (standard and outline appearances) now draws a
  solid, 2px outline with a 2px offset in the focus color
  (`--ngx-form-field-focus-color`), for every state — valid, invalid, and
  warning. Before, an invalid or warning field kept its danger/warning
  border unchanged on focus and only added a 25%-opacity box-shadow ring
  (1.53:1 for invalid, 1.40:1 for warning on white) — a keyboard user
  tabbing into an invalid field, for example from the error summary, could
  not always see where focus landed (WCAG 2.2 SC 2.4.7, SC 1.4.11). New
  tokens: `--ngx-form-field-focus-outline-width` (default `2px`) and
  `--ngx-form-field-focus-outline-offset` (default `2px`). The plain
  appearance is unaffected — it keeps drawing its own input-level focus
  outline (added in `#493`) and suppresses this new container outline so
  it never shows two at once.
- `--ngx-form-field-invalid-box-shadow` (default `none`) is a new public
  token for the invalid state's box-shadow ring. See the required-change
  section above for its role.
- See [THEMING.md — States & Focus](../../packages/toolkit/form-field/THEMING.md#states--focus)
  for the full token list and the plain-appearance interaction.
