## Upgrade from v1.0.0-rc.15

Scope: the RC.15-to-RC.16 upgrade. It has nineteen required changes:

- the form field wrapper's default border color is darker;
- the wrapper's warning ring defaults to `none`;
- dark mode now follows `color-scheme`, with new dark defaults, instead of
  `.dark` or the OS query;
- every field error and warning starts with a visually hidden prefix;
- a form with an error summary announces errors after a submit through the
  summary only;
- the full `NgxSignalFormsConfig` type has five new required members;
- the two character-count result types merged into one;
- a field's hint stays visible next to a blocking error or warning instead of
  hiding;
- the `vest` and `axe-core` peer floors are raised, and `axe-core` gets an
  upper bound;
- the `autoAria` config key is removed;
- `NgxFormFieldErrorSummary` no longer has a `warningStrategy` input;
- the root entry point keeps only the two visibility seams (`createErrorVisibility()`
  and `createWarningVisibility()`) (changes 12 to 18);
- helpers that only the toolkit uses left the root entry point, and
  `injectFieldControl`, `isFormFieldAppearance` and `isFormFieldOrientation` are
  deleted (change 13);
- `NgxHeadlessNotification` is removed, and the headless entry point drops
  duplicate exports (change 14);
- `NgxFieldIdentityProvider` and `NgxFormFieldErrorPlacement` each have one
  entry point (change 15);
- `NgxFormFieldErrorListStyle` and `NgxCharacterCountValue` are removed
  (change 16);
- `NgxSignalFormControlSemanticsDirective` is renamed to
  `NgxSignalFormControl` (change 17);
- `SignalLike` and `ReactiveOrStatic` get the `Ngx` prefix (change 18);
- five low-level headless helpers are no longer public (change 19).

Partial overrides through `provideNgxSignalFormsConfig()` are not affected
by the new config members. They are affected only if they pass `autoAria`
(change 10). The character-count merge (change 7), the `autoAria` removal (change 10),
the removed `warningStrategy` input (change 11) and the API surface review
(changes 12 to 19) are the only TypeScript APIs removed or renamed in this
release.

### Upgrade checklist and compatibility

- [ ] Confirm the installed toolkit version is RC.15. For earlier versions,
      first follow the [migration index](./README.md).
- [ ] Select `1.0.0-rc.16` in your package manager. Update the dependency and
      lockfile together.
- [ ] Keep compatible peers. Angular common/core/forms remain
      `>=22.0.0 <23.0.0`. Optional Vest now needs `>=6.3.0 <7.0.0` (raised
      from `>=6.0.0`), and optional axe-core now needs `>=4.13.0 <5` (raised
      from `>=4.5.0`, and now capped). See [compatibility](../COMPATIBILITY.md)
      and the [package manifest](../../packages/toolkit/package.json).
- [ ] Build and run your existing type-check and tests.

### Required changes

#### 1. `--ngx-form-field-border-color` now defaults to a darker, WCAG-compliant color

`--ngx-form-field-border-color` (which cascades from
`--ngx-form-field-color-border`) defaulted to `rgba(50, 65, 85, 0.25)` — a
border that met only 1.55:1 contrast against the field's white background
(2.21:1 in dark mode), below the WCAG 2.2 SC 1.4.11 (Non-text contrast) 3:1
floor. It is the only visible edge of a text input, so a low-vision user
could not always tell where a field ended.

It now defaults to `rgba(50, 65, 85, 0.7)` in light mode and
`rgba(249, 250, 251, 0.4)` in dark mode. WCAG 2.2 SC 1.4.11 exempts
disabled controls, so the 3:1 floor only applies to an enabled field. The
light-mode value clears 3:1 against every background an enabled field's
border was measured against: white (~4.35:1), `#f9fafb` (~4.17:1),
`#f3f4f6` (~3.96:1), and `#e5e7eb` (~3.52:1, a common page/card
background). `#f3f4f6` also happens to be `--ngx-form-field-color-disabled`
— the border clears 3:1 against it too, but that is incidental, not an
SC 1.4.11 requirement, since a disabled field is exempt. The dark-mode
value clears ~3.51:1 against the dark surface color (`#1f2937`). The
border reads darker (light mode) or lighter (dark mode) than before. If
your theme depends on the previous, lighter value, restore it explicitly:

```css
ngx-form-field-wrapper {
  --ngx-form-field-color-border: light-dark(
    rgba(50, 65, 85, 0.25),
    rgba(249, 250, 251, 0.25)
  );
}
```

A restored value below 3:1 re-introduces the original contrast failure —
prefer keeping the new default, or picking your own color at 3:1 or more,
over reverting.

#### 2. `--ngx-form-field-warning-box-shadow` now defaults to `none`

Before (the effective default — `--ngx-form-field-warning-color` has no
default of its own, so it needs the same fallback here that the wrapper
gives it internally):

```css
--ngx-form-field-warning-box-shadow: 0 0 0 4px
  color-mix(
    in srgb,
    var(--ngx-form-field-warning-color, #a16207) 25%,
    transparent
  );
```

After:

```css
--ngx-form-field-warning-box-shadow: none;
```

The 25%-opacity ring only reached 1.40:1 contrast on white — below the 3:1
floor — and a focused warning field now also draws a solid, higher-contrast
outline (see the addition below). Left at its old default, the ring would
sit in the same visual band as the new outline and double up. If you rely
on the ring, restore it:

```css
ngx-form-field-wrapper {
  --ngx-form-field-warning-box-shadow: 0 0 0 4px
    color-mix(
      in srgb,
      var(
          --ngx-form-field-warning-color,
          var(--ngx-form-field-color-warning, light-dark(#a16207, #fcd34d))
        )
        25%,
      transparent
    );
}
```

The `light-dark()` fallback matches the wrapper's own warning color in both
schemes, so the ring follows your app's `color-scheme` (see
[section 3](#3-dark-mode-follows-color-scheme-not-dark-or-the-os-query)).

The same change applies to the invalid state through the new
`--ngx-form-field-invalid-box-shadow` token — see the addition below; there
is no "before" value to restore since that token did not exist before this
release.

#### 3. Dark mode follows `color-scheme`, not `.dark` or the OS query

Before, the components used different dark-mode triggers:

- The wrapper switched on a `.dark` class through `:host-context()`. When
  the OS preferred dark and `.dark` was absent, it forced light colors.
- The error component switched on `prefers-color-scheme` only. In a light
  app on a dark OS, error text was `#fca5a5` on white (1.90:1) and warning
  text was `#fcd34d` on white (1.44:1).
- The hint, character count, marking legend, fieldset and error summary had
  no dark colors. In a `.dark` app, hint and count text was 1.29:1.

Now every color default is a `light-dark(<light>, <dark>)` pair. The
browser picks the side from the element's used `color-scheme`. The toolkit
has no `prefers-color-scheme` or `:host-context(.dark)` color rules left.
Public token names do not change, and a value you set on a public token
still wins.

An app that declares no `color-scheme` gets light colors, also on a dark
OS. If your app relied on the OS query or on a `.dark` class, declare the
scheme:

```css
/* Follow the OS (replaces the old prefers-color-scheme behavior) */
:root {
  color-scheme: light dark;
}

/* Or: class toggle (replaces the old .dark detection) */
:root {
  color-scheme: light;
}

:root.dark {
  color-scheme: dark;
}
```

If you set `--ngx-signal-form-error-color`, `--ngx-signal-form-warning-color`
or other color tokens per theme only to work around the old triggers, remove
those overrides. A single value on a token applies in both schemes; use
`light-dark()` in your own value to keep separate light and dark colors.

Other consumer-visible changes that ship with this release, none of them
requiring an action unless you built on the removed internals:

- A focused standard or outline-appearance textual field now draws a solid,
  2px outline (see the addition below) in addition to its existing
  border-color and box-shadow changes. If you already override
  `--ngx-form-field-focus-color`, the outline picks it up automatically.
- The invalid state's box-shadow ring is no longer built from an inlined,
  non-overridable `color-mix()` expression. It is now driven by the new
  `--ngx-form-field-invalid-box-shadow` token (default `none`).
- `--ngx-form-field-state-ring-opacity` no longer affects the invalid or
  warning rings, since both default to `none`. It still controls the
  focus-color ring on a valid field (`--ngx-form-field-focus-box-shadow`),
  which is unchanged.

#### 4. With an error summary, a submit announces through the summary only (#522)

The summary and each field error are `role="alert"` regions. Before, one
submit that revealed N field errors fired N + 1 assertive announcements at
once. Screen readers then cut speech off, stacked it, or read errors twice.

Now, when an `NgxFormFieldErrorSummary` sits inside a
`form[formRoot][ngxSignalForm]`:

- A field error that a submit reveals renders outside its own
  `role="alert"` region. It keeps the same `${fieldName}-error` id and the
  same look, so the control's `aria-describedby` still reads it.
- When the user edits the field and the error changes, the new error goes
  into the field's `role="alert"` region and announces as before.
- Forms without a summary, or with the summary outside the `<form>`, do not
  change.

**What to update.** Tests that find a submit-revealed field error by
`[role="alert"]` no longer find it. Find it by its id or its text:

```ts
// Before
page.locator('[role="alert"]').filter({ hasText: 'Username is required' });

// After
page.locator('#username-error');
```

To keep the old behavior, turn the feature off:

```ts
provideNgxSignalFormsConfig({ errorSummaryAnnouncesAlone: false });
```

#### 5. Field errors and warnings start with a visually hidden prefix (#498)

`NgxFormFieldError` now puts a visually hidden "Error: " or "Warning: " in
front of each message, inside the element that `aria-describedby` points to.
A screen reader reads "Error: Email is required" instead of relying on color
to tell an error from a warning (WCAG 1.4.1, 1.3.1). `NgxFormFieldErrorSummary`
and headless consumers do not render it.

This changes the element's `textContent`, the control's accessible
description, and ARIA snapshots. Exact-text assertions fail:

```ts
// Before
expect(error).toHaveTextContent('Email is required');

// After: match the full text, or match a part of it
expect(error).toHaveTextContent('Error: Email is required');
expect(error).toHaveTextContent(/Email is required/u);
```

Translate the prefix, or turn it off per channel, through the config:

```ts
provideNgxSignalFormsConfig({
  errorPrefixText: 'Fout:', // '' turns the error prefix off
  warningPrefixText: '', // no warning prefix
});
```

#### 6. The full `NgxSignalFormsConfig` type has five new members

`errorPrefixText`, `warningPrefixText` (#498), `errorSummaryAnnouncesAlone`
(#522), `characterCountLimitText` (#499) and `hideHintOnError` (#521) are
required members of
`NgxSignalFormsConfig`. Code that builds the full object itself, for example
a custom `NGX_SIGNAL_FORMS_CONFIG` provider with `useValue`, must add them:

```ts
{
  provide: NGX_SIGNAL_FORMS_CONFIG,
  useValue: {
    ...myConfig,
    errorPrefixText: 'Error:',
    warningPrefixText: 'Warning:',
    errorSummaryAnnouncesAlone: true,
    characterCountLimitText: 'Up to {max} characters',
    hideHintOnError: false,
  } satisfies NgxSignalFormsConfig,
}
```

`provideNgxSignalFormsConfig()` and `provideNgxSignalFormsConfigForComponent()`
take a partial `NgxSignalFormsUserConfig` and fill in the defaults, so calls
to them need no change.

#### 7. `CharacterCountResult` and `CharacterCountStateSignals` merged into `CharacterCountState`

`createCharacterCount()` returned `CharacterCountResult` and
`NgxHeadlessCharacterCount` implemented `CharacterCountStateSignals` — two
public types with identical fields. Both are gone. Import
`CharacterCountState` from `@ngx-signal-forms/toolkit/headless` instead:

```ts
// Before
import type {
  CharacterCountResult,
  CharacterCountStateSignals,
} from '@ngx-signal-forms/toolkit/headless';

// After
import type { CharacterCountState } from '@ngx-signal-forms/toolkit/headless';
```

`CharacterCountState.resolvedMaxLength` is `Signal<number | null>`, because
`hasLimit` is now a real signal instead of a hardcoded `true`. `null` means
no limit was configured or auto-detected — check `hasLimit()` before using
`resolvedMaxLength()` as a number. `remaining`, `isExceeded`, `percentUsed`,
and `limitState` stay non-nullable: they report `0`, `false`, `0`, and
`'ok'` respectively when no limit applies.

`createCharacterCount()`'s `maxLength` option is now optional
(`NgxReactiveOrStatic<number | null>`, previously required). A new
`useValidatorMaxLength` option (default `false`) makes the factory fall
back to the field's own `maxLength()` schema validator when `maxLength`
resolves to no explicit limit — the auto-detection
`NgxFormFieldCharacterCount` used to duplicate on its own. Existing calls
that always pass an explicit `maxLength` are unaffected.

`NgxHeadlessCharacterCount`'s `maxLength` input is unchanged (still
required), so its `hasLimit` always resolves to `true`, matching the
previous behavior — and its `resolvedMaxLength` stays `Signal<number>`
(not the nullable factory type), so directive consumers see no type
change at all.

#### 8. A field's hint stays visible next to a blocking error or warning (#521)

Before, `NgxFormFieldWrapper` hid a field's hint as soon as the field carried
a blocking error or warning. The hint's id stayed in `aria-describedby`, so a
screen reader still read it, but a sighted user lost the format instructions
right when the error said the value did not match them (WCAG 2.2 SC 3.3.2).

Now the hint stays visible next to the error by default. The error still
renders before the hint in the assistive row (layout is unchanged);
`aria-describedby` order is unchanged too.

**What to update.** A browser or e2e test that asserted the hint was hidden
during an error now fails, because the hint renders:

```ts
// Before
await expect(page.locator('#rating-hint')).not.toBeVisible();

// After
await expect(page.locator('#rating-hint')).toBeVisible();
```

To keep the old behavior, turn it on globally or per field:

```ts
provideNgxSignalFormsConfig({ hideHintOnError: true });
```

```html
<ngx-form-field-wrapper [formField]="form.email" hideHintOnError>
</ngx-form-field-wrapper>
```

See [ADR-0015](../decisions/0015-hints-stay-visible-while-an-error-shows.md).

#### 9. The `vest` and `axe-core` peer floors are raised (#515)

A new scheduled CI matrix tests the toolkit against the lowest and highest
version of each declared Node, Angular and peer-dependency range. It found
that the declared floors for two optional peers were already broken:

- `vest` `>=6.0.0 <6.3.0` fails to load. It imports named exports from
  `vest-utils`/`vestjs-runtime` that later releases inside `vest`'s own
  declared dependency range removed. For example, `vestjs-runtime@1.7.0` —
  the version `vest@6.0.0`'s own `^1.6.0` range resolves to today — dropped
  the `IsolateReorderable` export its bundle imports, and `vest-utils@2.0.17`
  — what `vest@6.1.x`/`6.2.x`'s own `^2.0.x` range resolves to — dropped the
  `tinyState` export those versions import. A plain `npm install vest@6.0.0`
  today pulls in a combination that fails either way.
- `axe-core` `>=4.5.0 <4.13.0` flags the toolkit's own a11y spec fixtures —
  for example `aria-prohibited-attr` for an `aria-labelledby` attribute on a
  role-less host in `auto-aria.aria-required-role.a11y.browser.spec.ts` —
  that later axe-core versions do not. `4.13.0` is the first version that
  passes the toolkit's browser suite outright.

Both floors are raised to the lowest version that passes:

```diff
  "peerDependencies": {
-   "axe-core": ">=4.5.0",
-   "vest": ">=6.0.0 <7.0.0"
+   "axe-core": ">=4.13.0 <5",
+   "vest": ">=6.3.0 <7.0.0"
  }
```

If your `package.json` pins `vest` or `axe-core` below these floors, bump the
pin. Most consumers already resolve to a version inside the new range,
because the old floors could not install cleanly in the first place.

#### 10. The `autoAria` config key is removed (#584)

`autoAria` on `NgxSignalFormsUserConfig` and `NgxSignalFormsConfig` had no
effect. No directive read it, so `autoAria: false` left
`NgxSignalFormAutoAria` writing `aria-invalid`, `aria-required` and
`aria-describedby`. The key is gone, and passing it is now a type error.

Delete `autoAria: true` from your config. It changes nothing. No config key
replaces `autoAria: false` for the whole app. If you passed it, pick the
opt-out that fits:

```ts
// Before
provideNgxSignalFormsConfig({ autoAria: false });

// After: every control that declares this kind with ngxSignalFormControl
provideNgxSignalFormControlPresets({
  composite: { ariaMode: 'manual' },
});
```

A preset reaches only a host that declares its kind with
`ngxSignalFormControl`. A plain `<input [formField]>` has an inferred kind,
but the preset's ARIA mode does not reach it, so auto-ARIA stays on. Add the
kind to every host the preset must cover:

```html
<app-date-range ngxSignalFormControl="composite" [formField]="form.dates" />
```

For one control, add `ngxSignalFormControlAria="manual"` when the control
writes its own ARIA, or `ngxSignalFormAutoAriaDisabled` to turn auto-ARIA
off on that host. Use `provideNgxSignalFormControlPresetsForComponent()` to
scope a preset to one component.

#### 11. `NgxFormFieldErrorSummary` no longer has a `warningStrategy` input (#587)

The styled summary lists blocking errors only. It never rendered warning
rows, so `warningStrategy` had no visible effect on it. The input is gone. A
template that binds it no longer compiles:

```html
<!-- Before -->
<ngx-form-field-error-summary [formTree]="form" warningStrategy="immediate" />

<!-- After -->
<ngx-form-field-error-summary [formTree]="form" />
```

Delete the binding. If you need warning timing in a summary, use
`NgxHeadlessErrorSummary` from `@ngx-signal-forms/toolkit/headless`. It keeps
the `warningStrategy` input, and you render `warningEntries()` under
`shouldShowWarnings()` yourself. See the
[summary contracts](../COMPLEX_NESTED_FORMS.md).

#### 12. The root entry point keeps only the visibility seams (#511)

The root entry point exported many visibility-timing helpers. Only `createErrorVisibility()`
and `createWarningVisibility()` are public now. `createFieldPresentation()`
stays public for wrapper authors. The rest were building blocks of these
functions. The toolkit still uses them, but they left the public entry point.

Removed from `@ngx-signal-forms/toolkit`:

- `combineShowErrors`. It had no caller. Use `computed(() => a() || b())`.
- `createShowErrorsComputed`, `shouldShowErrors` and `shouldShowWarnings`.
  Use `createErrorVisibility()` or `createWarningVisibility()`.
- `resolveErrorDisplayStrategy`, `resolveWarningStrategy`,
  `resolveStrategyFromContext`, `resolveWarningStrategyFromContext` and
  `resolveSubmittedStatusFromContext`. The two visibility functions run the
  same cascade: input, form context, config default, then `'on-touch'`.

```ts
// Before
import {
  createShowErrorsComputed,
  resolveStrategyFromContext,
} from '@ngx-signal-forms/toolkit';

const formContext = injectFormContext();
const strategy = computed(() =>
  resolveStrategyFromContext(this.mode(), formContext),
);
const showErrors = createShowErrorsComputed(field, strategy, submittedStatus);

// After
import { createErrorVisibility } from '@ngx-signal-forms/toolkit';

const showErrors = createErrorVisibility(field, {
  strategy: this.mode,
  submittedStatus,
});
```

`createErrorVisibility()` reads the `ngxSignalForm` context through dependency
injection. Call it in an injection context, such as a field initializer.

#### 13. Helpers that only the toolkit uses left the root entry point (#511)

These functions had no caller outside the toolkit. Three leave the root entry
point, and three are deleted:

- `getDefaultValidationMessage` is step 3 of `resolveValidationErrorMessage()`.
  Call `resolveValidationErrorMessage()` instead.
- `readNgxSignalFormControlSemantics` and `inferNgxSignalFormControlKind` are
  steps inside `resolveNgxSignalFormControlSemantics()`. Call that function
  instead.
- `injectFieldControl` is deleted, with no replacement. It had no caller in
  the toolkit or the demos.
- `isFormFieldAppearance` and `isFormFieldOrientation` are deleted. Compare the
  value with the literals, or type it as `FormFieldAppearance` or
  `FormFieldOrientation`.

```ts
// Before
import {
  getDefaultValidationMessage,
  isFormFieldAppearance,
} from '@ngx-signal-forms/toolkit';

const text = getDefaultValidationMessage(error);
const ok = isFormFieldAppearance(value);

// After
import { resolveValidationErrorMessage } from '@ngx-signal-forms/toolkit';

const text = resolveValidationErrorMessage(error);
const ok = value === 'standard' || value === 'outline' || value === 'plain';
```

#### 14. `NgxHeadlessNotification` is removed, and the headless entry point drops duplicate exports (#511)

**`NgxHeadlessNotification` is removed.** It had no consumer in the toolkit or
the demos. The RC.12 guide said it "remains available". That is no longer
true. `NgxHeadlessToolkit` now holds five directives. Use
`NgxHeadlessErrorState` with its `errorsOverride` input for a list of errors
that you computed. The caller owns timing, as before. The types
`NotificationStateSignals` and `ResolvedNotificationMessage` are gone too.

```html
<!-- Before -->
<section
  ngxHeadlessNotification
  #notice="notificationState"
  [errors]="addressErrors"
  fieldName="address"
>
  @if (notice.showErrorContainer()) { ... }
</section>

<!-- After -->
<section
  ngxHeadlessErrorState
  #state="errorState"
  [errorsOverride]="addressErrors"
  fieldName="address"
>
  @if (state.hasErrors()) { ... }
</section>
```

**One home for each shared helper.** These names now come from the root entry
point only. Change the import path:

| Removed from `@ngx-signal-forms/toolkit/headless` | Import it from `@ngx-signal-forms/toolkit` |
| ------------------------------------------------- | ------------------------------------------ |
| `createUniqueId`                                  | yes                                        |
| `readDirectErrors`                                | yes                                        |
| `ErrorMessageRegistry` (type)                     | yes                                        |

**Two more headless exports are gone.** `summarizeFieldOptionality` is the
plain twin of `createFieldOptionalitySummary()`. Use the factory. The type
`ErrorSummaryEntryData` had a second name, `ErrorSummaryEntry`. Use
`ErrorSummaryEntry`.

#### 15. `NgxFieldIdentityProvider` and `NgxFormFieldErrorPlacement` each have one entry point (#511)

Two names were exported from two entry points. Each now has one home:

- `NgxFieldIdentityProvider` comes from `@ngx-signal-forms/toolkit` only. RC.14
  added an optional re-export from `@ngx-signal-forms/toolkit/form-field`. It
  is gone. It provides a core service that any wrapper needs, not only the
  built-in form field.
- `NgxFormFieldErrorPlacement` comes from `@ngx-signal-forms/toolkit/form-field`
  only. Only the wrapper and the fieldset use it.

```ts
// Before
import { NgxFieldIdentityProvider } from '@ngx-signal-forms/toolkit/form-field';
import type { NgxFormFieldErrorPlacement } from '@ngx-signal-forms/toolkit';

// After
import { NgxFieldIdentityProvider } from '@ngx-signal-forms/toolkit';
import type { NgxFormFieldErrorPlacement } from '@ngx-signal-forms/toolkit/form-field';
```

#### 16. `NgxFormFieldErrorListStyle` and `NgxCharacterCountValue` are removed (#511)

Both were aliases of another exported type. Use the original name:

| Removed from `@ngx-signal-forms/toolkit/assistive` | Use instead                                                     |
| -------------------------------------------------- | --------------------------------------------------------------- |
| `NgxFormFieldErrorListStyle`                       | `NgxFormFieldListStyle` (same entry point)                      |
| `NgxCharacterCountValue`                           | `CharacterCountValue` from `@ngx-signal-forms/toolkit/headless` |

```ts
// Before
import type {
  NgxCharacterCountValue,
  NgxFormFieldErrorListStyle,
} from '@ngx-signal-forms/toolkit/assistive';

// After
import type { NgxFormFieldListStyle } from '@ngx-signal-forms/toolkit/assistive';
import type { CharacterCountValue } from '@ngx-signal-forms/toolkit/headless';
```

#### 17. `NgxSignalFormControlSemanticsDirective` is renamed to `NgxSignalFormControl` (#511)

The class was the only exported class with a `Directive` suffix. It now
matches its selector, `[ngxSignalFormControl]`, the way `NgxSignalForm` matches
`ngxSignalForm`. The interface `NgxSignalFormControlSemantics` keeps its name.
Only the class name changes. The selector and the inputs stay the same.

```ts
// Before
import { NgxSignalFormControlSemanticsDirective } from '@ngx-signal-forms/toolkit';

@Component({
  imports: [NgxSignalFormControlSemanticsDirective],
  // ...
})
class MyControlHost {
  readonly semantics = inject(NgxSignalFormControlSemanticsDirective);
}

// After
import { NgxSignalFormControl } from '@ngx-signal-forms/toolkit';

@Component({
  imports: [NgxSignalFormControl],
  // ...
})
class MyControlHost {
  readonly semantics = inject(NgxSignalFormControl);
}
```

The `NgxFormField` bundle already includes the directive, so templates that
import the bundle need no change.

#### 18. `SignalLike` and `ReactiveOrStatic` get the `Ngx` prefix (#511)

Both names are generic. Your code or another library can export the same name.
They stay public, because the headless option types use them. They are now
`NgxSignalLike` and `NgxReactiveOrStatic`. Only the names change.

```ts
// Before
import type { ReactiveOrStatic, SignalLike } from '@ngx-signal-forms/toolkit';

// After
import type {
  NgxReactiveOrStatic,
  NgxSignalLike,
} from '@ngx-signal-forms/toolkit';
```

#### 19. Five low-level headless helpers are no longer public (#666)

These five helpers are not exported from `@ngx-signal-forms/toolkit/headless`
any more. They were steps inside the public factories. No demo or other entry
point used them. The factories still use them inside the package.

| Removed                      | Use instead                                                               |
| ---------------------------- | ------------------------------------------------------------------------- |
| `readFieldFlag`              | The typed field state (`field().invalid()`), or `createFieldStateFlags()` |
| `readErrors`                 | `field().errorSummary()`, or `createErrorState()`                         |
| `toErrorSummaryEntry`        | `createErrorSummaryEntries({ fieldState })`; it accepts any subtree       |
| `resolveFieldNameFromError`  | The `fieldName` of a summary entry                                        |
| `focusBoundControlFromError` | The `focus()` and `canFocus` of a summary entry                           |

Behavior does not change. The summary still falls back from `errorSummary()` to
`errors()`, ignores malformed state, and keeps entry keys, `canFocus` and focus
the same.

A lone `ValidationError` has no public mapper now. Build entries from the field
subtree with `createErrorSummaryEntries({ fieldState })`. The options that
`toErrorSummaryEntry` took move to that factory: pass `errorMessages` for the
message registry and `labelResolver` for field labels. Warning entries always
strip the warning prefix. Error entries do not.

```ts
// Before
import {
  focusBoundControlFromError,
  readErrors,
  toErrorSummaryEntry,
} from '@ngx-signal-forms/toolkit/headless';

const errors = readErrors(form());
const entries = errors.map((error) => toErrorSummaryEntry(error));
focusBoundControlFromError(errors[0]);

// After
import { signal } from '@angular/core';
import { createErrorSummaryEntries } from '@ngx-signal-forms/toolkit/headless';

const summary = createErrorSummaryEntries({
  fieldState: form,
  showErrors: signal(true),
  showWarnings: signal(true),
});
const first = summary.entries()[0];
if (first?.canFocus) {
  first.focus();
}
```

`createErrorSummaryEntries()` also drops errors on hidden or disabled fields.
It dedupes by field, kind and message, so two fields that fail the same rule
both stay in the list. Read `entry.fieldName` for the label. Render an entry as
plain text when `entry.canFocus` is `false`.

### Additions and compatibility

- A focused textual field (standard and outline appearances) now draws a
  solid, 2px outline with a 2px offset in the focus color
  (`--ngx-form-field-focus-color`), for every state — valid, invalid, and
  warning. Before, an invalid or warning field kept its danger/warning
  border unchanged on focus and only added a 25%-opacity box-shadow ring
  (1.53:1 for invalid, 1.40:1 for warning on white) — a keyboard user
  tabbing into an invalid field, for example from the error summary, could
  not always see where focus landed (WCAG 2.2 SC 2.4.7, SC 1.4.11). New
  tokens: `--ngx-form-field-focus-outline-width` (default `2px`) and
  `--ngx-form-field-focus-outline-offset` (default `2px`). The plain
  appearance is unaffected — it keeps drawing its own input-level focus
  outline (added in `#493`) and suppresses this new container outline so
  it never shows two at once.
- `--ngx-form-field-invalid-box-shadow` (default `none`) is a new public
  token for the invalid state's box-shadow ring. See the required-change
  section above for its role.
- New config keys: `errorPrefixText` (default `'Error:'`) and
  `warningPrefixText` (default `'Warning:'`) (#498), and
  `errorSummaryAnnouncesAlone` (default `true`) (#522). The #522 decision is
  recorded in [ADR-0012](../decisions/0012-error-summary-announces-alone.md).
- `characterCountLimitText` (default `'Up to {max} characters'`) (#499) is a
  new config key. `NgxFormFieldCharacterCount` renders it as a visually
  hidden element linked into the field's `aria-describedby`, so a screen
  reader states the limit on focus even with `[liveAnnounce]` off.
- See [THEMING.md — States & Focus](../../packages/toolkit/form-field/THEMING.md#states--focus)
  for the full token list and the plain-appearance interaction.
- New `hideHintOnError` config key (default `false`) and matching
  `NgxFormFieldWrapper` input, to restore the pre-RC.16 hide-hint-on-error
  behavior (#521). See [ADR-0015](../decisions/0015-hints-stay-visible-while-an-error-shows.md).
- In a form without `ngxSignalForm`, auto-ARIA now follows the app or
  component `defaultErrorStrategy` for `aria-invalid` and the error id in
  `aria-describedby` (#585). Before, it always used `on-touch`, so the ARIA
  could lag behind the visible message. You do not need to change code. If
  you added `ngxSignalForm` only to fix this timing, you can remove it.
- `ngxHeadlessErrorState` has a new `renders` input (`'both'`, `'errors'` or
  `'warnings'`, default `'both'`) for a template that renders one channel only
  (#644). It keeps the id of the missing element out of `aria-describedby`.
  The field visibility registry descriptor has a
  new optional `shouldShowErrors` signal for `aria-invalid`.
