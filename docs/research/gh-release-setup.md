# Research: release setup for a GitHub-hosted npm library (October 2026)

Question: what is the current best way to release `@ngx-signal-forms/toolkit` from a repository whose `main` branch needs a pull request, status checks and one approval, and how does this repository's setup compare?

Sources are primary only: GitHub docs and changelog, npm docs, the GitHub repositories of the release tools, and the installed Nx 23.3.0 package. Each source is listed with its date at the end. GitHub and npm docs pages carry no date unless noted. Those are marked "undated, fetched 2026-10-12". Sources older than 2025-10-12 are marked **possibly stale**.

Each claim is labelled as either **Sources say** (taken from a cited source) or **Inference** (my reading of what the sources imply for this repository).

## Summary

Switch to tag-only releases. The tag push starts `publish.yml`, the release gate runs there, the version is written into the built `package.json` from the tag, and the GitHub release is created only after npm accepts the package. This removes the GitHub App, its private key and its ruleset bypass, and it keeps OIDC publishing, provenance and the environment approval.

**Adopted (2026-10-12):** a variant of tag-only. The release-prep pull request bumps `packages/toolkit/package.json` together with the migration guide, and the maintainer tags the merged commit. The version stays in `main`, so the ng-packagr question below does not apply. The Nx `manifestRootsToUpdate` change in recommendation 3 was not made. Recommendations 1, 4 and 5 are in `publish.yml` and `docs/CONTRIBUTING.md`, and `release.yml` is removed. Recommendation 2 changed: the publish jobs now use the npm bundled with Node 24.18.0 (11.16.0), which supports OIDC but is still below the 11.21.0 that #663 needs. A migration guide is now required only for a release with breaking changes.

## What the sources say

### Q1. Releasing from a repository with a protected default branch

**Trusted publishing (npm).** Sources say:

- A GitHub Actions trusted publisher is bound to an owner, a repository and a workflow filename. The environment name is optional. Trusted publishing needs npm CLI 11.5.1 or later and Node 22.14.0 or later, and it only works on GitHub-hosted runners ([npm: trusted publishers](https://docs.npmjs.com/trusted-publishers), edited 2026-10-06).
- When a workflow is started through `workflow_call` or `workflow_dispatch`, npm validates the calling workflow's filename. In a `workflow_call` chain that is not the file that runs `npm publish` (same page).
- OIDC covers `npm publish`, `npm stage publish` and, when the configuration allows it, dist-tag changes (same page). Dist-tag access is off by default. It is turned on per configuration with **Allow npm dist-tag** and needs npm CLI 11.21.0 or later on the 11 line, or 12.2.0 or later ([changelog 2026-09-30](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/); version numbers from the npm docs page).
- npm recommends setting **Require two-factor authentication and disallow tokens** once trusted publishing works (npm trusted publishers page).
- With staged publishing, CI uploads the package to a queue and a human maintainer approves it with 2FA on npmjs.com or in the CLI. It needs npm CLI 11.15.0 or later ([changelog 2026-05-22](https://github.blog/changelog/2026-05-22-staged-publishing-and-new-install-time-controls-for-npm/)). A trusted publisher can be limited to staging only, in which case every CI publish goes through that approval (npm trusted publishers page).

**Provenance.** Sources say that trusted publishing from GitHub Actions generates provenance automatically, without `--provenance`. The repository and the package must be public ([npm: trusted publishers](https://docs.npmjs.com/trusted-publishers); [npm: generating provenance statements](https://docs.npmjs.com/generating-provenance-statements), edited 2026-05-04). **Not verified:** whether a staged publish keeps provenance. The staged-publishing changelog does not say.

**Environment protection (GitHub).** Sources say ([deployments and environments reference](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments), undated, fetched 2026-10-12; [managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments), undated, fetched 2026-10-12):

- An environment can list up to six required reviewers, and one approval is enough.
- **Prevent self-review** stops the person who started the run from approving it.
- By default, administrators can bypass the rules. This can be turned off.
- Deployment refs can be limited to protected branches or to named branch and tag patterns.
- Environment secrets reach a job only after its rules pass.
- If a workflow references an environment that does not exist, GitHub creates it with no protection rules.

**Tag protection.** Sources say:

- Rulesets can target tags. **Restrict creations**, **Restrict updates** and **Restrict deletions** limit those actions on matching refs to bypass actors ([available rules for rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets), undated, fetched 2026-10-12).
- Immutable releases lock a release's assets. They also lock its tag, which then cannot be moved or deleted ([changelog 2025-10-28](https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/)). This repository has immutable releases enabled; the `v1.0.0-rc.15` release reports `immutable: true`.

**CI-created refs.** Sources say:

- Events caused by `GITHUB_TOKEN` do not start new workflow runs. The exceptions are `workflow_dispatch` and `repository_dispatch` ([GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token), undated, fetched 2026-10-12).
- Since 2026-06-11, a pull request opened by `github-actions[bot]` can run workflows once a user with write access approves the run ([changelog 2026-06-11](https://github.blog/changelog/2026-06-11-bot-created-pull-requests-can-run-workflows-if-approved/)).
- Whether `GITHUB_TOKEN` may create pull requests is controlled by one setting, **Allow GitHub Actions to create and approve pull requests**, which also controls whether it may approve them ([Actions settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), undated, fetched 2026-10-12). In this repository the setting is off.
- **Not verified:** whether an approval from `github-actions[bot]` counts toward a ruleset's required approvals.

**Pinning and least privilege.** Sources say that pinning an action to a full commit SHA is "the only way to use an action as an immutable release". GitHub also recommends the minimum `GITHUB_TOKEN` permissions and OIDC over long-lived secrets ([secure use reference](https://docs.github.com/en/actions/reference/security/secure-use), undated, fetched 2026-10-12). A repository policy can require SHA pinning ([changelog 2025-08-15](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/), **possibly stale**).

**Pull request approvals.** Sources say that a pull request's author cannot approve it, and that owners and admins can merge without an approving review ([approving a pull request with required reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews), undated, fetched 2026-10-12).

### Q4. Is a GitHub App as a ruleset bypass actor accepted practice?

Sources say:

- GitHub supports it. GitHub Apps are listed as eligible bypass actors ([creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), undated, fetched 2026-10-12).
- GitHub's ruleset exemption feature is recommended for "trusted, high-volume automation". A standard bypass is described as a "break glass" action that leaves prominent audit signals ([changelog 2025-09-10](https://github.blog/changelog/2025-09-10-github-ruleset-exemptions-and-repository-insights-updates/), **possibly stale**).
- GitHub's 2026 Actions security roadmap names GitHub Apps among trusted automation in actor rules ([GitHub blog, 2026-03-26](https://github.blog/news-insights/product-news/whats-coming-to-our-github-actions-2026-security-roadmap/)).
- OpenSSF Scorecard's Branch-Protection check scores `EnforceAdmins` as false when any bypass actor exists on a rule, "regardless of if they are admins" ([Scorecard checks.md](https://github.com/ossf/scorecard/blob/main/docs/checks.md), last changed 2026-10-10).
- The semantic-release GitHub Actions recipe says `GITHUB_TOKEN` cannot push to a protected branch. It calls a personal access token in its place a security risk, acceptable only where every developer already has admin rights. It also advises against committing `package.json` changes during a release ([semantic-release GitHub Actions recipe](https://semantic-release.gitbook.io/semantic-release/recipes/ci-configurations/github-actions), undated, fetched 2026-10-12). That GitBook site states it is discontinued.

I found no GitHub source that discourages an App bypass actor.

Inference:

- This is accepted practice. Its cost is a standing, non-human credential that skips review and status checks.
- Scorecard already scores this repository's `main` ruleset as not enforcing admins, because the Admin role is a bypass actor. Adding the App would not change the score.

### Q5. `actions/create-github-app-token`: `app-id` and `client-id`

Sources say:

- `client-id` was added and `app-id` deprecated in v3.1.0, released 2026-04-11 ([release notes](https://github.com/actions/create-github-app-token/releases/tag/v3.1.0); commit `e6bd4e6`).
- In v3.2.0 (2026-05-12, the latest release, and the commit `bcd2ba49` this repository pins), `action.yml` declares:
  - `client-id`: "GitHub App Client ID".
  - `app-id`: "GitHub App ID", with `deprecationMessage: "Use 'client-id' instead."`
  - Neither input is required on its own.
- At runtime the action prefers `client-id` and falls back to `app-id`. It fails when neither is set (commit `e6bd4e6` message).
- The README asks for the App's Client ID in a repository variable such as `APP_CLIENT_ID`, and says the legacy `app-id` is still accepted ([README](https://github.com/actions/create-github-app-token)).

So `app-id` still works, and `client-id` replaces it. `app-id` takes the App's numeric ID. `client-id` takes the Client ID shown on the App's settings page.

This repository's last real release run (2026-10-08) printed the deprecation warning. It then failed with "The 'client-id' (or deprecated 'app-id') input must be set to a non-empty string".

### Nx 23.3.0 and release pull requests

Checked against the installed package (`nx@23.3.0`, resolved from `node_modules/nx`).

Sources say:

- `nx release` has these subcommands: `version`, `changelog`, `publish`, `plan` and `plan:check` (`dist/src/command-line/release/command-object.js`). None of them opens a pull request.
- The only pull-request handling in `dist/src/command-line/release/` parses `(#123)` references in commit messages for changelogs (`utils/git.js:431-474`, `utils/remote-release-clients/github.js:276-282`).
- `schemas/nx-schema.json` has no release-PR option.
- Nx creates GitHub releases as published, not as drafts (`make_latest: 'legacy'`, `prerelease` passed through, in `utils/remote-release-clients/github.js:191-301`).
- The Nx CI guide versions locally with `nx release --skip-publish`, pushes the commit and tag, and publishes from a `v*.*.*` tag workflow. It does not mention release pull requests ([Nx: publish in CI/CD](https://nx.dev/docs/guides/nx-release/publish-in-ci-cd), undated, fetched 2026-10-12).
- Nx supports tag-only versioning:
  - `release.version.manifestRootsToUpdate` can point at the dist directory only (`schemas/nx-schema.json:1196`).
  - `currentVersionResolver` accepts `git-tag`, which is the default (`schemas/nx-schema.json:1224`; `config/config.js:169`).
  - The Nx guide calls this "Scenario 3", where the tracked `package.json` is no longer the source of truth for the version ([Nx: updating version references](https://nx.dev/docs/guides/nx-release/updating-version-references), undated, fetched 2026-10-12).

Inference: an Nx release PR would be a custom workflow around `nx release version`. Nx has no built-in support for one.

## How the current setup differs from each alternative

- **Release PR.** Today the version commit goes to `main` without review, through the App. A release PR puts it through the same review and checks as any other change. The human approval needs no bypass, because the bot is the author. The cost is one extra PR per release and an extra click to approve the workflow runs.
- **Tag-only.** Today `packages/toolkit/package.json` on `main` records each version, and the App pushes it. Tag-only stops committing versions; only the built `dist/packages/toolkit/package.json` carries one. No release step writes to `main`, so the App, the `push` job and the bundle hand-off all go away. The `release` and `push` jobs today check that the release commit changes only the version. That check has nothing to guard once no commit exists.
- **release-please / changesets.** Both would replace Nx release and the custom renderer in `tools/release/`, which enforces the migration-guide rule from `docs/migrations/README.md`. Both default to writing `CHANGELOG.md`, which this project does not keep.
- **semantic-release.** It removes the manual `workflow_dispatch` choice of bump and prerelease id. Releases would follow every push to the release branch, which does not fit release candidates that are cut by hand.
- **Shared by all designs.** `publish.yml` already follows the npm and GitHub guidance. It uses OIDC with no npm token, splits the job that installs dependencies from the job that holds `id-token: write`, pins actions by SHA, and checks that the tag matches the version and that the commit is on `main`. Both `--provenance` and `NPM_CONFIG_PROVENANCE` are redundant under trusted publishing, but harmless.

## Gaps in the current setup, ranked

1. **The GitHub release is created before npm publishes.** The `github-release` job in `release.yml` runs right after the push, while `publish.yml` is still waiting for approval. For rc.15 the release was created at 22:32:39 and the Publish run started at 22:32:43. Immutable releases are on, so the tag is locked once the release exists. If the publish is rejected at the approval gate or fails, the GitHub release stays up for a version that is not on npm, and the version number is spent. The migration guide written for that number then documents a hop that never ships, which `docs/migrations/README.md` warns against.
2. **The App push path has not completed a release.** The App credentials and the bypass entry are not configured. The first real run, on 2026-10-08, stopped at the token step, so nothing was pushed. The step also still uses the deprecated `app-id` input. rc.15 shipped under the earlier flow.
3. **The pinned npm version blocks #663.** Both publish jobs install `npm@11.20.0`. OIDC dist-tag changes need 11.21.0 or later.
4. **`main` must stay still from dispatch to push.** The `release` job takes up to 35 minutes, and then the `push` job waits for approval. The push requires `main` to be exactly one commit behind the release commit, so any merge in that window fails the run, including a Dependabot auto-merge. The bundle is kept for one day, so an approval given later than that cannot reuse the run.
5. **There is no rollback runbook.** `docs/CONTRIBUTING.md` says how to release but not how to recover. The cases it should cover are a failed push, a failed or rejected publish, a published bad version, and a wrong dist-tag.

## Recommended changes

Each item fits one PR. Items 1 and 2 apply whichever design is kept.

1. **Create the GitHub release after a successful publish.** Move the `nx release changelog` step into a job in `publish.yml` that `needs: publish`, with `contents: write`, and no `id-token`. Remove the `github-release` job from `release.yml`. A rejected publish then leaves no immutable release behind, and in tag-only the tag can still be deleted.
2. **Raise the npm pin to 11.21.0 or later in both publish jobs.** Re-check the sigstore note in the step comment, then finish #663 on top.
3. **Tag-only, step 1: version the dist manifest from the tag.** In `nx.json`, set `release.version.manifestRootsToUpdate` to `dist/{projectRoot}` (Nx Scenario 3) and keep `currentVersionResolver: git-tag`. In the `publish.yml` build job, after the build, run `nx release version <tag version>` with `--git-commit=false --git-tag=false`. Drop the `version` field from `packages/toolkit/package.json`, or keep a fixed placeholder. **Not verified:** whether ng-packagr accepts a missing `version`.
4. **Tag-only, step 2: move the release gate into `publish.yml`.** The build job runs the checks that `release.yml` runs today, before the approval gate: full toolkit suite, coverage, package checks and size, isolation build, affected e2e, and the release-notes preflight that requires `docs/migrations/v<version>.md`.
5. **Tag-only, step 3: shrink `release.yml` to a preflight.** Keep it as a dry run that resolves the next version and previews the notes. It pushes nothing. Delete the `push` job and the App token step. Rewrite the "Release" section of `docs/CONTRIBUTING.md`: run the preflight, then `git tag -a v<version> -m "Release <version>" <sha on main>` and push the tag. Add the recovery table above.
6. **Maintainer settings (no PR):**
   - Confirm that a `v*` tag ruleset restricts creation, update and deletion to Admin. Tag-only depends on it.
   - Remove the App setup that is no longer used.
   - Consider a stage-only trusted publisher, so that each release also needs a 2FA approval on npmjs.com.

If tag-only is rejected and the version must stay in `main`, the next best option is a custom release PR around `nx release version`. It needs no bypass actor.

## What could not be verified

- Whether a staged npm publish keeps provenance.
- Whether an approval from `github-actions[bot]` counts toward a ruleset's required approvals.
- Whether release notes stay editable once a release is immutable.
- Whether ng-packagr builds a `package.json` that has no `version`.
- What release bodies release-please writes with `skip-changelog`, and what changesets writes with `changelog: false`.
- This repository's trusted publisher configuration on npmjs.com, which needs an npm login.
